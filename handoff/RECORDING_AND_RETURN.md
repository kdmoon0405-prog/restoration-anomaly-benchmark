## 두 기록의 역할

### PROGRESS.md

실제로 수행한 작업과 관측 결과를 시간순으로 기록한다. 기존 파일을 이어 쓰고,공개 사본에는 상대경로와 공개 가능한 metadata를 사용한다. 다음 항목을 개발 기능 또는 실험 family/완료단위마다 남긴다.

- 시작·완료 시각,상태와 실제 실행 모델/환경
- 작업 목적,실행 source commit과 protocol/config,입력·split·calibration 참조
- run-id,실행 명령,생성 파일과 receipt
- 실측 결과·실패·수정·검증,미측정/추정 범위
- 다음 실행과 차단 항목

같은 사실을 각 subunit마다 복사하지 않고 manifest/CSV를 연결한다. 준비·실행중·완료·실패 상태를 실제 artifact로 구분한다.

### 비공개 RESEARCH_EVOLUTION_LOCAL.md

선택에 따른 근거와 설계 변화를 기록한다. 기존 ignored/untracked 결정 노트가 있으면 이어 쓴다. 새 파일이 필요하면 outputs/private-decisions/jihyuk/RESEARCH_EVOLUTION_LOCAL.md를 사용하고 Git ignore·tracked 상태를 확인한다. 사용자의 중앙 notes/RESEARCH_EVOLUTION_LOCAL.md와 연결할 수 있도록 아래 정보를 남긴다.

- 검토 날짜와 결정 ID,관련 run-id/source commit
- 해결하려는 문제와 검증할 질문
- 검토한 대안과 각 대안의 입력·자원·일정 조건
- 판단 근거가 된 실제 CSV/JSON·코드·문헌 또는 명시적 가정
- 선택한 방법과 선택 이유,보류·기각한 방법과 이유
- 실험 전에 정한 성공/실패 기준과 지표·calibration/threshold 결정 데이터
- 실행 후 관측값과 해석,설계를 유지·수정한 이유
- 수정 전후,남은 질문과 다음 행동

확인 가능한 판단을 간결하게 쓴다. 당시 작성한 기록과 나중에 정리한 해석을 구별하고,기록이 없는 과거 판단은 미기록으로 남긴다. 실제 근거가 없으면 가정·미확인으로 표시한다.

## 실험을 병행하는 방법

현재 protocol과 기준이 고정된 작업은 Fable 설계 검토와 함께 계속한다. 저장 clean-map control,사진 없이 가능한 synthetic 검증·구현,입력이 확보된 촬영 실험 등 승인된 queue를 진행한다. 지혁의 bank-domain 실행과 CPU consumer 소유권은 유지한다.

새 방법·추가 실험은 질문,대조군,입력·split,지표와 선택 기준,예산을 짧게 기록하고 해당 실험의 첫 test 비교 전에 고정한다. 이 기록은 실행 가능한 범위를 정리하는 절차이며 설계 보고서 전체의 완료를 기다리는 조건으로 사용하지 않는다. 승인된 범위 안의 선택과 실행은 자율적으로 이어간다.

GPU 실험이 도는 동안 설계·근거 검토·그림·원고를 진행할 수 있다. RAM/VRAM이 경합하면 무거운 실험은 순차 처리하고 가벼운 작업을 병행한다. 기존 자원 guard를 유지한다. 사진·데이터가 미수신인 작업은 독립적인 구현/저장결과 분석으로 이어간다.

## 반환

기능·category/session 등 검증 가능한 단위가 끝날 때 code·schema·익명 수치·공개 PROGRESS와 receipt를 기존 feature branch/handoff로 반환한다. 긴 실험은 완료된 단위부터 전달한다.

같은 반환 묶음에 실제 private 결정 노트의 증분 또는 전체본도 사용자에게 비공개로 전달한다. 전달 시 마지막 결정 ID/날짜와 대응하는 공개 run-id/commit을 알려 중앙 노트에 통합할 수 있게 한다. 이 실제 노트와 RGB/GT/raw arrays는 기존 비공개 경로를 유지하며 stage/commit/push에서 제외한다. 공개용 결정 요약이 필요하면 비공개 내용을 검토해 별도 문서로 작성한다.
